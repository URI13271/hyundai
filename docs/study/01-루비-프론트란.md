# Ruby 프론트란

프론트는 사람이 보는 화면이다. Ruby 프론트는 그 화면의 HTML을 Ruby가 만든다는 뜻이지, 브라우저에 Ruby 엔진을 넣는다는 뜻이 아니다.

```text
브라우저  --요청-->  Ruby 서버  --HTML-->  브라우저가 그림
```

React로 치면 컴포넌트가 브라우저 안에서 다시 그려진다. 이 앱은 반대다. 버튼을 누르면 서버가 다음 화면 HTML을 통째로 보내고, 브라우저가 그 문서로 교체한다.

## 이 앱에서 프론트인 것

| 보이는 것 | 만드는 곳 |
| --- | --- |
| 글, 버튼, 좌석 카드 | `views/screen.erb` |
| 색, 가로·세로, 다크 | `public/app.css`, `public/adaptive.css` |
| 1.5초 뒤 자동 이동, 마이크 허용 | `public/app.js` |
| “지금 어떤 화면인가” | `lib/drive_talk/game.rb`의 `@screen` |
| HTML로 조립 | `lib/drive_talk/view.rb` |

게임 규칙처럼 보이는 `game.rb`도 이 저장소에서는 화면 상태다. 참여 좌석, 현재 차례, 집계는 화면이 그리려고 들고 있는 값이다. 프로세스가 죽으면 사라진다. 그걸 진짜 저장소로 옮기는 일은 백엔드다.

## 버튼은 링크가 아니라 폼이다

홈의 게임 시작은 이런 모양이다.

```erb
<form method="post" action="/start">
  <button class="btn dark" data-need-mic>게임 시작</button>
</form>
```

브라우저가 `POST /start`를 보낸다. 서버는 화면 이름을 바꾸고, `303`으로 `GET /shuffle`을 지시한다. 브라우저는 그 주소를 다시 연다. 새로고침을 해도 시작이 두 번 나가지 않는다. 이 패턴 이름은 Post/Redirect/Get이다.

자바스크립트로 `fetch`해서 조각만 갈아 끼우지 않았다. 폼은 스크립트가 죽어도 동작한다. 이 앱의 스크립트는 타이머와 마이크 허용만 한다.

## 화면 이름은 심볼이다

서버는 한글 제목으로 화면을 고르지 않는다. `:splash`, `:home`, `:mic`, `:shuffle`, `:seats`, `:read`, `:answer`, `:done` 여덟 개다. 템플릿의 `case @game.screen`이 이 이름으로 블록을 고른다.

주소와 이름은 1:1이 아니다. 낭독과 답변은 둘 다 `/question`이다. 구분은 `@screen`이 한다. 표는 `lib/drive_talk.rb`의 `SCREEN_PATH`다.

## 앞으로 이 방식을 쓰는 이유

- 화면 추가가 파일 세 곳이다. 상태 메서드, 라우트, ERB 분기.
- 새로고침이 곧 현재 상태다. 숨은 클라이언트 저장소가 없다.
- CSS는 그냥 CSS다. 빌드 단계가 없다.

한계도 같이 알고 있어야 한다. 화면 일부만 바꾸는 일은 서툴다. 지금은 목소리 확인이 끝나면 페이지를 한 번 더 받는다. 그 정도가 이 방식의 업데이트다. 조각 갱신이 필요해지면 그때 Hotwire를 얹는다. 지금은 얹지 않는다.
