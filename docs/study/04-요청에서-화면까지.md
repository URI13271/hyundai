# 요청에서 화면까지

한 연결은 요청 하나다. `connection: close`라서 응답을 보내면 소켓을 닫는다. keep-alive를 공부 범위에서 뺐다.

## 서버가 켜질 때

```ruby
tcp = TCPServer.new("0.0.0.0", port)
loop { Thread.new(tcp.accept) { |sock| new(sock).process } }
```

`TCPServer`는 포트에 붙는다. `accept`는 브라우저가 붙을 때까지 기다린다. 붙으면 스레드를 하나 만들고, 그 소켓만 `Server` 인스턴스가 처리한다.

스레드를 쓴 이유는 한 요청이 렌더하는 동안 다음 연결을 받기 위해서다. 다만 판을 만지는 구간은 `Store`의 `Mutex`가 한 번에 하나만 들여보낸다. 좌석을 동시에 눌러도 판이 반으로 갈라지지 않는다. 대가는 화면 생성이 줄 선다는 것이다. 이 앱 규모에서는 그 대가가 맞다.

## 요청을 읽는 법

브라우저가 보내는 텍스트는 이런 모양이다.

```text
POST /hear HTTP/1.1
content-type: application/x-www-form-urlencoded
content-length: 8

choice=a
```

`read_request`가 하는 일은 네 가지다.

1. 빈 줄(`\r\n`) 전까지가 머리글이다. 16KB를 넘으면 버린다.
2. 첫 줄을 메서드, 주소, HTTP 버전으로 나눈다.
3. `content-length`만큼 본문을 읽는다. 길이를 모르면 어디서 끝나는지 알 수 없다.
4. 주소의 쿼리와 본문을 `CGI.parse`로 해시처럼 만든다.

결과는 심볼 키 해시 하나다. `:method`, `:path`, `:query`, `:form`, `:cookies`, `:headers`.

쿠키 원문은 `theme=dark; dt=abc`다. `parse_cookie`가 세미콜론으로 나누고 `CGI.unescape`로 값을 되돌린다.

## 테마는 게임보다 먼저

`dispatch`는 판을 찾기 전에 쿠키를 고친다.

- `theme`는 `light`, `dark`, `system`만 받는다.
- `layout`은 `auto`, `landscape`, `portrait`만 받는다.
- `demo=1`만 데모 쿠키를 켠다. 끄는 주소는 없다.

허용 목록이 있는 이유는 쿼리 문자열을 그대로 클래스 이름에 넣지 않기 위해서다. `body_class`가 이 값을 HTML class로 출력한다.

`pref_only?`가 참이면 `route`를 건너뛴다. `GET /question?theme=dark`가 답변을 제출하면 안 된다. 테마만 저장하고 현재 화면으로 다시 보낸다.

## 판을 찾는 법

쿠키 `dt`가 세션 id다. 없거나 비어 있으면 `SecureRandom.hex(8)`로 만든다. `@games[id] ||= Game.new(id)`는 그 id의 판이 없으면 하나 만든다.

응답에 `set-cookie: dt=...`를 넣는 경우는 브라우저가 보낸 id와 지금 id가 다를 때뿐이다. 첫 방문이 그 경우다.

이 해시는 메모리에만 있다. 서버를 재시작하면 진행 중이던 판은 없다. 그게 목 세션의 한계이고, 일부러 그대로 뒀다.

## 라우트

`route`는 상태를 바꾸기만 한다. HTML을 만들지 않는다.

| 요청 | 호출 |
| --- | --- |
| `POST /enter` | `advance_from_splash` |
| `POST /start` | `start` |
| `POST /mic`, `GET /mic` | `show_mic` |
| `POST /mic/open` | `grant_mic` |
| `POST /ready` | 섞기면 `finish_shuffle`, 낭독이면 `finish_read` |
| `POST /seat` | `toggle` |
| `POST /begin` | `begin_round` |
| `POST /hear` | `hear` |
| `POST /settle` | 아무것도 안 함 |
| `POST /replay` | `replay` |
| `POST /next` | `next_step` |
| `POST /leave` | `ask_leave` |
| `POST /stay` | `stay` |
| `POST /quit` | `quit` |
| `POST /again` | `again` |
| `POST /home` | `home` |

표에 없는 주소는 `case`가 아무것도 안 한다. 그래도 마지막에 현재 화면으로 보낸다. 모르는 POST가 500이 되지는 않는다.

`/health`만 예외다. 본문 `ok`를 주고 판을 찾지 않는다.

## 언제 HTML을 만들고 언제 보내는가

```ruby
dest = SCREEN_PATH.fetch(game.screen)
if req[:method] == "GET" && req[:path] == dest && !pref_only?(req)
  html = View.new(...).render
end
```

세 조건이 맞을 때만 200과 HTML이다.

- 메서드가 GET이다.
- 주소가 지금 화면의 주소와 같다.
- 테마·레이아웃·데모만 바꾸러 온 요청이 아니다.

하나라도 아니면 `303`이다. `location`은 `SCREEN_PATH`의 값이다.

그래서 `POST /start`의 실제 왕복은 이렇다.

```text
브라우저  POST /start
서버      화면을 :shuffle 로 바꿈
서버      303 Location: /shuffle
브라우저  GET /shuffle
서버      200, shuffle HTML
```

주소창은 항상 현재 화면을 가리킨다. POST 주소에 머무르지 않는다.

`read`와 `answer`는 둘 다 `/question`이다. 그래서 답변 제출도 `303 /question`이고, 브라우저는 같은 주소를 다시 연다. 화면 이름만 바뀌어 있다.

## 응답을 쓰는 법

```ruby
HTTP/1.1 303 See Other
location: /shuffle
set-cookie: dt=...
content-length: 0
connection: close
```

상태 문장은 `REASON`에서 찾는다. `set-cookie`가 여러 개면 헤더를 여러 줄로 쓴다. `Array(value)`가 그 일이다. 본문 길이는 글자 수가 아니라 `bytesize`다. 한글은 한 글자가 3바이트다. 길이를 글자 수로 적으면 브라우저가 본문을 덜 읽는다.

## 정적 파일

`/assets/app.css`는 `public/app.css`다. `delete_prefix("/assets/")`로 상대 경로를 만든다. 확장자로 Content-Type을 고른다. css, js, woff2만 표에 있다. 나머지는 `application/octet-stream`이다.

`File.binread`는 인코딩 변환 없이 바이트를 읽는다. 폰트에 필요하다.

## 손으로 따라갈 요청

서버를 띄운 뒤 다른 터미널에서 한 판의 앞부분을 보낸다. `-D -`는 응답 머리글을 보여 준다. `-c`와 `-b`는 쿠키를 파일에 저장하고 다시 보낸다.

```sh
rm -f /tmp/dt.jar
curl -sS -D - -c /tmp/dt.jar -b /tmp/dt.jar -o /dev/null -X POST http://127.0.0.1:4567/enter
curl -sS -D - -c /tmp/dt.jar -b /tmp/dt.jar -o /dev/null -L http://127.0.0.1:4567/home
```

첫 응답에 `303`과 `set-cookie: dt=`가 있어야 한다. 두 번째는 `-L`이 리다이렉트를 따라가 홈 HTML을 받는다.

`curl -L -X POST`는 쓰지 않는다. curl은 303 다음에도 POST를 유지하는 경우가 있다. 브라우저는 303 뒤를 GET으로 연다. 둘을 같다고 보면 안 된다.
